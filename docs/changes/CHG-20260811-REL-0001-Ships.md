# REL-0001 ships

`counters.REL` read `0` for six months across 85 features — not because nothing shipped, but because nothing ever drew a line around a shippable state. **This is the first line, and it is now closed.**

## What changed

- [[REL-0001]] is `released`, `version: 1.0.0`, `tag: v1.0.0`, `date: 2026-08-11`. Edwin's decision, taken once the gate was green and nothing technical was left ([[CHG-20260811-Gate-Green]]).
- **A local annotated git tag `v1.0.0`.** Not pushed, and that is the rule rather than an omission: committing is reversible, publishing is not, and pushing in this project is a person clicking the action ([[FEAT-0055]]).
- The note's *"Build: not applicable — this is not a versioned artifact"* is **amended, not deleted**. Still no build and nothing to install; what the version buys is that the state is addressable — `git checkout v1.0.0` returns the record and the tool exactly as the suite verified them.

## Impact

**The `Unreleased` card starts measuring.** [[TASK-0315]]'s rule is that only a `released` note ships anything, so the card counted every done feature while REL-0001 was `draft`: **86**. It now reads **59** — the 27 features this release names are shipped, and what remains is work that predates it and was never claimed.

*Corrected after independent review: this said **70**, a figure carried over from [[TASK-0315]] and [[FEAT-0072]], where the corpus held 70 done features and the card landed on 59 for an entirely different reason. Run against this commit's own parent, `unreleased_payload` returns 86. The arithmetic in the sentence beside it — minus the 27 named — only works from 86, which is what should have caught it. The commit message carries the same stale number and cannot be corrected without moving the `v1.0.0` tag, so it is corrected here instead.*

`test_the_real_repo_reports_its_actual_state` was written asserting the opposite (`since is None`) with a failure message naming this exact day: *"if that is real, this project's first release has happened and this assertion should record it."* It does now, including that no feature REL-0001 names is still counted as unreleased.

## Independent review — 2026-08-11 (model:claude-opus-5, fresh context, separate agent session) — changes-requested

Reviewed from the notes and the diff, without the authoring session's reasoning. **The release itself stands**: 34 of 34 gating checks are settled with evidence on every line, the one that was not walked is documented, and `status: released` / `version: 1.0.0` / `tag: v1.0.0` are internally consistent with the note and with `STATUSES.md`. Nothing found here argues for reversing it. The current payload was verified — `since: REL-0001, 2026-08-11`, `count: 59` — and 59 is right: 86 completed features minus the 27 this release names.

Three findings, all in the record rather than the code:

1. **The "before" number is wrong, and its own paragraph disproves it.** This note says the card read **70** and now reads **59**. Run against `014889d^` — the commit's own parent — `unreleased_payload` returns **86**. The transition was 86 → 59, which is exactly the 27 features the release names; 70 → 59 is 11, and the sentence explaining it ("the 27 features this release names are shipped") cannot produce that. **70 is a stale figure** carried from [[TASK-0315]] and [[FEAT-0072]], written when the corpus held 70 done features and only 11 of the named ones were done — where it landed on 59 for a different reason. The coincidence is why it survived. It is repeated in the commit message.
2. **`unreleased_payload`'s docstring now states the opposite of the corpus.** `cockpit.py:2312-2314` still reads *"That matters here today — REL-0001 is `draft` and names 27 features, none of which have shipped."* The test that asserted the same thing was updated in this commit; the docstring beside the code was not.
3. **`SNAPSHOT.yaml` carries `status: released` and a `note:` that says otherwise.** The `items.releases.REL-0001.note` field still ends *"Still `draft`, and now for a second reason: 17 leg-1 Tier 1/2 checks unwalked AND four phases barely started."* `sync-snapshot.py` propagates status and deliberately leaves prose alone, so this one is curation and it was missed — in the file CLAUDE.md calls the canonical machine-readable context for agents.

Also noted, not filed: `test_the_real_repo_reports_its_actual_state` now checks 4 of the 27 named features against the unreleased rows. Asserting the whole set is one line and would catch a membership bug in the 23 it does not name; the floor moved 50 → 40 against a live 59, which is looser than the state it guards.

## Response to the review — 2026-08-11

**The 70 is corrected to 86** in the body above, with why it survived. The commit message carries the same stale figure and is left alone: correcting it means rewriting `014889d`, which moves the `v1.0.0` tag off the commit it was cut for — a worse trade than a wrong number in a message with the right number in the note beside it.

**The docstring and the snapshot note are fixed.** `unreleased_payload` said *"REL-0001 is `draft` and names 27 features, none of which have shipped"*; `SNAPSHOT.yaml`'s `items.releases.REL-0001.note` ended *"Still `draft`…"*. Both were prose beside data that had moved — one in a docstring the test update did not reach, one in the field `sync-snapshot.py` deliberately never touches.

**The floor and the sample are both tightened.** `test_the_real_repo_reports_its_actual_state` now reads the release note's own `features:` list — all 27 — and asserts none of them appears in the unreleased rows, with the floor back to 50. The verdict on this note is the reviewer's to change, not mine.

## Independent review, round two — 2026-08-11 (model:claude-opus-5, same reviewer, fresh look at `73827d1`) — approved

All three findings fixed and re-established independently: the card's before-figure now reads **86**, which is what `unreleased_payload` returns against `014889d^`; the docstring and `SNAPSHOT.yaml`'s release note both say what is true; and the test reads all 27 names out of the release note's `features:` list rather than sampling four, with the floor back to 50 against a live 59.

**On the commit message keeping the stale 70 — I agree with the trade.** `v1.0.0` is an annotated tag on `014889d`; correcting the message rewrites that commit and moves the tag off the state it was cut for. A commit message is a dated artifact of what was believed at the time, and the durable record beside it now carries both the right number and the reason the wrong one survived. That is a better outcome than a tag pointing at a commit nobody cut.

One note for the future rather than a finding: **this is the second time a figure travelled by being copied from a note where it was true.** 70 came from [[TASK-0315]] intact and landed on 59 by a different route, which is why nothing looked wrong. Numbers in prose have no provenance; the ones worth trusting are the ones a test recomputes — as `test_the_real_repo_reports_its_actual_state` now does for the 27.
