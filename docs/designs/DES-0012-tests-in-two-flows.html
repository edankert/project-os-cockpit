DES-0012 · accepted 2026-08-18 · all five decided

Tests in two flows

The cockpit has one population of tests and two questions to answer with it: is this feature done? and can we ship this set? Today the tests view answers neither, because it is organised by three different principles at once. This proposes one structure, and asks you for five decisions.

Decisions

  1. D1 What groups the list
  2. D2 Manual vs automated
  3. D3 Tier's future
  4. D4 What a release contains
  5. D5 Where a walk happens

The problemThe list is sorted three ways at once

The tests view builds its groups from two functions that never agreed on what a group is. _tests_groups buckets non-acceptance tests by verification state — owed, failing, stale, verified. _acceptance_tier_groups buckets acceptance tests by tier, which is a statement about lifetime. Nothing buckets by what the test covers, which is the only thing either flow actually asks about.

So "Needs a walk" sits outside the tier sections not by choice but because the two lists have no common axis. Folding one into the other is not a layout change — it is the decision below.

The frameTwo flows, one population, different scopes

Both flows consume the same tests. What differs is how much they ask about at once — and that is exactly what covers: already encodes.

The code already has the primitive: blocking_for(subjects) takes a set of subjects and returns what holds them. blocking() is the subjects=None case. The dev flow and the release flow are the same query at two zoom levels — and no surface presents them that way.

A defect this design has to resolve

command: and automation: both answer "manual or automated", and they disagree by construction. command: asks whether this note has a runner. automation: asks whether the thing the check describes is covered by automated tests living somewhere else. In your-trainer: 22 full, 181 partial, 376 manual — a populated, useful field that no list surfaces, sitting beside a field ADR-0034 declared the single answer to the same question.

You asked for a manual/automated distinction. We have two, and picking one is D2.

Decision 1What groups the list

Three candidates. Each makes one flow easy and costs something on the other.

A

Tier, extended to every test

smallest change

Give non-acceptance tests a tier so all 600 sit in the same three sections. "Needs a walk" folds in as a row badge rather than a section.

ForClosest to what you asked for, and the view barely moves.
AgainstTier is a lifetime statement, not a scope — it answers neither flow's question. And ADR-0034 already resolved to retire it.
B

Scope — what the test covers

superseded by D1

Group by the feature (or release) the test covers. Tier, level and execution become row attributes and filter chips. The same view serves both flows by changing what is in scope.

ForThe only axis both flows share. Percentage complete becomes meaningful per feature and per release. "Organise tests by release" falls out for free.
Against80 groups in your-trainer when nothing is scoped, and 83 checks cover nothing at all — they would need a home, or backfilling.
C

Level — what it exercises

Group by level:: unit, integration, system, acceptance.

ForEvery test has one, and it is the industry's own vocabulary.
Against22 tests in this repo carry no level. And it answers "how deep does this go", which is a question neither flow asks.

Recommendation: B, with A's shape as the default view. Group by scope, but when nothing is selected, collapse to the tier summary you already know — so the landing page stays three lines, and choosing a feature or a release expands into its own tests. Scope is the structure; tier is the default zoom.

D1 — decided: group by surface

Not feature — Edwin: “scope them based on where they sit in the application, the surface they are supposed to test.” That field already exists: area:, and Tier 1's values are the surfaces — Profile Management, Hardware Connectivity, Workout Execution, Monetization & Licensing. 25 groups, not 80. Areas do not span tiers, so the structure is tier → surface → rows — which the generated page had until I flattened it hours before writing this. Reverted.

Decision 2Which field means "automated"

Both exist and both are populated. They are not redundant — they answer genuinely different questions — but only one can drive a badge that says "automated" without lying.

  • Keep command: as the single answer (status quo, ADR-0034). A test is automated iff something can run it. automation: becomes descriptive prose and stops being read. Cost: your-trainer's 22 full and 181 partial checks all read as "manual", which is true of the check and misleading about the coverage.
  • Surface both, named differently. command: → "who runs it"; automation: → "how much a machine already covers". Two chips on a row. Cost: two vocabularies for a reader to hold.
  • Retire automation:, express it as covers: — a check that says "the automated LicenseSeatResolverTest covers the caps" should link that test rather than describe it in a field. Most honest, most work, and it makes the roll-up derived rather than authored.

D2 — decided: command: only

automation: stops answering “who runs this”. The cost, stated: 22 full and 181 partial checks read as manual. The argument for it: 66 Tier 3 checks sit in an area called “Moved from Tier 1 / Tier 2 — Fully Automated” while carrying automation: manual. The field already disagrees with itself.

Decision 3Whether tier survives

ISS-0208 is open on this and it now blocks D1. ADR-0034 decision 6 says tier survives "only if it earns its place as a lifetime field". Under option B it stops being structure and becomes an attribute — which is either the retirement that ADR intended, or the demotion that saves it.

There is a live sub-question underneath: six Tier 3 checks in your-trainer have never been walked and cover nothing. TESTING.md says Tier 3 does not gate a release. Either they are stale notes to retire, or a never-walked check should gate whatever its tier — that is a 60 → 66 move on the gate.

D3 — decided: tiers stay, and Tier 3's lifecycle was already written

The names are your-trainer's own — TESTING.md defines Feature / Regression / Verification and the cockpit copies them verbatim. They name why a test was created, which is why they read oddly beside a surface. Tier 3 is already “promoted or removed after a verified release”, never reopened. What is missing is anyone doing it: 66 of Tier 3's 74 checks are the unit-test-replacement holding pen, marked “remove after the next release” and never removed. That subsumes the six unwalked rows — Tier 3 is a housekeeping obligation, not a gate question.

Decision 4What a release contains

Today a release's contents are derived — "32 features unshipped since REL-0012" — or frozen at Mark released. There is no middle state, which is the state a preparing release is actually in. REL-0013 is preparing: 2026-08-16 with features: [].

The field already exists and works: REL-0001 carries 27 entries. What is missing is a way to fill it other than by hand. Once it is filled, blocking_for(release.features) makes the release page report itself rather than the whole suite — and "organise tests by release" is the same query.

Safety property: naming contents must be opt-in. A picker that changed the meaning of features: [] would rewrite the gate for eleven historical releases.

D4 — decided, and platform enters it

Agreed as proposed, plus: iOS and Android features and phases have their own releases today. The picker is platform-aware — platform: already exists and the nav already filters on it, so the candidate list narrows to the release's platform. A release with no platform takes both, which is how the two converge later without a migration.

Decision 5Where a walk happens

ADR-0035 (accepted, built today) says a release page reports and records nothing — walking happens where the procedure is visible. If tests organise by release, the temptation returns immediately: a release view listing its own tests is exactly where a person clearing a gate stands.

D5 — decided: one verb, and it is not “walk”

Edwin: “can you stop talking about ‘walking’.” Dropped in the prose and in the product. TASK-0495 changed the verb from Run to Walk because a person walks a procedure and a machine runs a command — and D2 removes that premise. With command: the only answer, one verb covers both: a test with a command is run by a runner, one without is run by a person. Run returns, and the guard that made Walk permanent is inverted. ADR-0035 still holds: a release page reports, it does not record.
