Plate E · Proposed

The review desk (~review) — where the agent's asks become decisions

Should this live on the project screen? Split it by role. Reviewing a proposal set or stepping through a manual test is a session — it needs the whole stage, context, and actions — while the project screen's job is to be glanceable. So: the overview announces (typed rows in Waiting-on-you, a count badge on the mode icon) and a new virtual page ~review — the same pattern as ~overview and ~agents — acts. Everything below runs on rails that already exist — and introduces no new status anywhere: ADRs, requirements, and tests queue on their existing intake states (proposed / draft / ready); feature/task sets queue as dispatch-ledger review requests (FEAT-0025) while their notes sit at plain backlog; accepting stamps the existing reviewed_by / review_date / review_verdict fields (the independent-review convention); session provenance comes from the hooks (FEAT-0019); write-back has its precedent in the interactive checkboxes (TASK-0074). Two views of the same screen: a proposal review, then a manual test run. One boundary the desk must keep: it is a queue, and queues empty — while the two founding asks (validate a feature/phase/release with acceptance tests; keep the project's design input visible) are records, and records grow. The queue is the doorbell; the durable homes are exhibited after the windows — acting on a queue row always writes into one of them.

v1 assumed live states for effect. This pass audits every status the design leans on against the actual corpus (frontmatter of every note, 2026-07-26) and against who writes it, when. The finding that shapes the whole design: this repo's work is bursty — an agent session sets doing, ships, and flips everything terminal at close-out, so the overview is mostly viewed in the quiet between sessions. The durable states are the human-shaped ones: things waiting on review, decisions, execution, or closure.

Notes & data

The redesign moves no idiom the cockpit hasn't already established — squares, chips, the muted REQ-0012 palette, uppercase section labels — it reweights them. Two principles did all the work: state before history (focus, attention, and in-flight items outrank charts of the past) and one fact, one place (the donut section died because the mix-bars in the tiles state the same numbers in situ).

The context pane — three honest options

Today the pane has a job on note screens (links/backlinks) but not on overview screens. v1 proposed a "meanwhile" column of live state; the states audit undermined that — live state is bursty, so that column would usually restate "idle." Three options that survive the audit:

Option A — the record column (recommended; shown in plates C and D). Decisions, Verification, Library — plus phase-scoped acceptance tests and decisions on drill-down. Always populated (6 ADRs, 19 tests, references exist on every real project), never stale by construction, and it answers "where are the ADRs and acceptance tests" — which no cockpit surface currently does: today ADRs are only reachable by browsing the Library tree.

Option B — collapse it by default on overview screens. The stage takes the 280 px; the panel-right toggle restores it. Cheapest to build, and honest: if the column has no job, width is the better spend. Defensible combined with A-as-opt-in.

Option C — move the commits panel there. Keeps the stage one section shorter, but commit rows want horizontal room for their item chips; at 280 px they degrade to two lines per commit. Weakest option — commits earn their full-width slot in the stage.

The review desk — one governance decision first

Plate E's surfaces are mostly plumbing that exists (statuses, dispatch, write-back). What does not exist is the policy: today LIFECYCLE lets preflight create planning artifacts and proceed straight to implementation. Making acceptance a gate — dispatch refuses a set without an accepting review_verdict — is a lifecycle change that deserves its own ADR, which is why the mock's queue contains "ADR-0007 · Approval gate for planning artifacts" as its first item. (Per the owner's constraint the gate predicate is the review fields, never a status: statuses record lifecycle, the ledger records the queue, the review fields record the verdict.) Two defensible shapes: advisory (everything reviewable, nothing blocked — the desk is a lens) or gated by type (FEAT / REQ / ADR require acceptance; TASK breakdowns under an accepted FEAT auto-accept). Recommend starting advisory, measuring how often review changes the plan, then deciding — the same evidence-first lesson ADR-0006 taught.

Retiring the Active and Recent modes

With Review in the strip, the mode bar consolidates from seven to six. Active (FEAT-0036) duplicates what the redesigned overview now carries ambiently — the focus band and phase rows show in-flight work, the progress rail and strip work tab show it live — and the states audit found the mode empty outside sessions anyway. Recent is superseded by the commits panel (git-anchored, item-linked — strictly more truthful than a recently-touched list) with ⌘P and history back/forward covering the jump-back use. Caveats, so the docs stay honest: this is a button retirement, not an API one — nav?mode=active still feeds the phase-less Now board and the strip work tab, and mode=recent stays server-side per the FEAT-0008 stability rule; phase-less projects' default mode falls back from Active to Overview (whose Now board shows the same data); and FEAT-0036's Active-mode UI is partially superseded, which its notes should record.
